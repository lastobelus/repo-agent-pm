## Agent Commentary (2025-12-17)

Your “Process Churn Antipattern” writeup is accurate, and (importantly) it’s a *known failure mode* for process work: the moment the formalization becomes a second job, it stops being a tool.

The key distinction to preserve is:

- **A practice** (lightweight, intuitive, flexible)
- **A protocol** (strict, complete, requires compliance)

The sequential-markdown approach is valuable precisely because it’s a practice. The spec should not accidentally turn it into a protocol.

### What to do about it (principle)

#agent-recommendation Treat the “spec” as a *field guide*, not a contract.

Meaning:

- Keep the document short.
- Prefer “defaults + escape hatches” over enumerating all possibilities.
- Make every optional mechanism explicitly optional.
- Add a disclaimer that it is descriptive (what worked) rather than prescriptive.

### Option 1 vs Option 2

Both are good; they optimize for different risks.

#### Option 1: Put a pin in the spec

This is the right move if your risk is “formalization causes you to stop using the practice.”

#agent-recommendation If you choose this: reduce the spec to a single "How to start" snippet + 3 principles:

- Latest `#status/active` file is truth
- Put real work only in **Agent Action** blocks
- Agent summarizes back into the file

Everything else becomes “nice-to-have suggestions,” or gets deleted until re-earned.

I like your idea of a “seed” note at the top of a `000-initial-iteration.md`. The seed is the *product*; the rest is commentary.

#### Option 2: Minimum remaining TODO work, then 10 real iterations

This is the right move if your risk is “we’re designing in the abstract.” Real iterations will tell you which parts matter.

#agent-recommendation If you choose this: set a very narrow success criterion for the spec:

- after 10 iterations, can a clean-context agent pick up with only the latest iteration doc + repo tree?

If yes, you win; don’t expand the spec.

### A hybrid that avoids the trap

#agent-recommendation Do Option 2 first, but do Option 1’s disclaimer now.

In practice:

- Add a one-paragraph disclaimer at the top of the spec ("practice, not protocol; optional conventions; keep it lightweight").
- Freeze the spec structure for 10 iterations.
- After 10 iterations, prune: delete anything that didn’t prove necessary.

This keeps you using the process while preventing the spec from turning into an ever-growing taxonomy.
